## 1. Executive Implementation Summary

Phase 5 completes the end-to-end digital onboarding journey for Indian MSMEs by connecting initial business discovery, product recommendations, quotation generation, consent-driven digital KYC, and synthetic registry validation with confirmed order placement, operational assignment, partner fulfilment, simulated activation, and unified customer tracking.

```
Customer Onboarding → AI Advisory → Product Recommendations → Quote Preview → Smart KYC
      ↓
Synthetic Registry Verification (GSTIN / Udyam)
      ↓
Order Placement (Confirmed Prototype Request & Frozen Snapshot)
      ↓
Operations Assignment & Monitoring (`/operations`)
      ↓
Partner Fulfilment & Progress Tracking (`/partner`)
      ↓
Operations Simulated Activation
      ↓
Customer Order Tracking & Historical Audit (`/orders`)
```

Phase 5 was implemented natively within the existing FastAPI backend, SQLite persistence architecture, and Next.js App Router frontend without introducing secondary databases, third-party authentication servers, or external provisioning infrastructure.

## 2. Core Functional Modules

### A. Quote-to-Order Conversion (`POST /api/v1/orders`)
- **Actor Authorization**: Restricted strictly to authenticated users with the `CUSTOMER` role.
- **Applicant Scoping**: Validates that the requested `applicant_id` belongs to the authenticated customer principal (`principal.applicant_ids`).
- **Prerequisite Validation**: Re-validates that the applicant exists and contains an authoritative, latest persisted quotation preview generated by the pricing engine.
- **Explicit Confirmation**: Requires `{ "confirmed": true }` in the request body. Submissions with `confirmed: false` are rejected with HTTP 422 Unprocessable Entity.
- **Duplicate Prevention & Idempotency**: Inspects existing orders for the applicant. If an active order (status other than `CANCELLED`) exists, the request is rejected with HTTP 409 Conflict.
- **Server-Side Trust**: Frontend-submitted pricing, fees, line items, and product eligibility flags are ignored. All snapshot values are computed server-side directly from the persisted quote preview.

### B. Immutable Pricing & Product Snapshot
When an order is placed, an authoritative `OrderSnapshot` is generated and serialized as JSON into the `orders.snapshot_json` column.
- **Captured Attributes**: `snapshot_version` (v1), `quote_id`, full `line_items` array (product names, quantities, unit prices, monthly subtotals, one-time setup subtotals, minimum contract months), aggregate `total_monthly_min_inr`, `total_monthly_max_inr`, `total_one_time_setup_inr`, `quote_created_at`, and the prototype commercial disclaimer.
- **Immutability Guarantee**: Pydantic models are frozen (`model_config = ConfigDict(frozen=True)`). Once written to SQLite, subsequent applicant profile edits, catalogue changes, or new quote generations never alter the persisted order record.

### C. State Machine & Lifecycle Transitions
The backend enforces a deterministic finite state machine defined in `backend/app/models/order.py`:

```
ORDER_PLACED ───────────► ASSIGNED ───────────► FULFILMENT_IN_PROGRESS
     │                         │                               │
     ├───────────┐             ├───────────┐                   ├───────────┐
     ▼           ▼             ▼           ▼                   ▼           ▼
  ON_HOLD    CANCELLED      ON_HOLD    CANCELLED            ON_HOLD    CANCELLED
     ▲                         ▲                               ▲
     └───────────┼─────────────┴───────────┼───────────────────┘
                 │ (OPERATIONS resume)     │
                 │                         │
                 ▼                         ▼
        FULFILMENT_COMPLETED ──► ACTIVATION_PENDING ──► ACTIVATED (Terminal)
                 │                         │
                 ├───────────┐             ├───────────┐
                 ▼           ▼             ▼           ▼
              ON_HOLD    CANCELLED      ON_HOLD    CANCELLED
```

#### Transition Permissibility Matrix
- `ORDER_PLACED` → `ASSIGNED`, `ON_HOLD`, `CANCELLED`
- `ASSIGNED` → `FULFILMENT_IN_PROGRESS`, `ON_HOLD`, `CANCELLED`
- `FULFILMENT_IN_PROGRESS` → `FULFILMENT_COMPLETED`, `ON_HOLD`, `CANCELLED`
- `FULFILMENT_COMPLETED` → `ACTIVATION_PENDING`, `ON_HOLD`, `CANCELLED`
- `ACTIVATION_PENDING` → `ACTIVATED`, `ON_HOLD`, `CANCELLED`
- `ON_HOLD` → `ORDER_PLACED`, `ASSIGNED`, `FULFILMENT_IN_PROGRESS`, `CANCELLED` (Restricted to authorized `OPERATIONS` resume actions)
- `ACTIVATED` & `CANCELLED` are terminal states (no transitions permitted).

#### Transition Role Authorization Matrix
- `("ORDER_PLACED", "ASSIGNED")`: `OPERATIONS`
- `("ORDER_PLACED", "ON_HOLD")`: `OPERATIONS`
- `("ORDER_PLACED", "CANCELLED")`: `OPERATIONS`, `CUSTOMER`
- `("ASSIGNED", "FULFILMENT_IN_PROGRESS")`: `PARTNER` (Assigned partner only)
- `("ASSIGNED", "ON_HOLD")`: `OPERATIONS`
- `("ASSIGNED", "CANCELLED")`: `OPERATIONS`
- `("FULFILMENT_IN_PROGRESS", "FULFILMENT_COMPLETED")`: `PARTNER` (Assigned partner only)
- `("FULFILMENT_IN_PROGRESS", "ON_HOLD")`: `OPERATIONS`, `PARTNER`
- `("FULFILMENT_IN_PROGRESS", "CANCELLED")`: `OPERATIONS`
- `("FULFILMENT_COMPLETED", "ACTIVATION_PENDING")`: `PARTNER`, `OPERATIONS`
- `("FULFILMENT_COMPLETED", "ON_HOLD")`: `OPERATIONS`
- `("FULFILMENT_COMPLETED", "CANCELLED")`: `OPERATIONS`
- `("ACTIVATION_PENDING", "ACTIVATED")`: `OPERATIONS` (Simulated activation gate)
- `("ACTIVATION_PENDING", "ON_HOLD")`: `OPERATIONS`
- `("ACTIVATION_PENDING", "CANCELLED")`: `OPERATIONS`
- `("ON_HOLD", "*")`: `OPERATIONS` only

### D. Operations Dashboard (`/operations`)
- Accessible only to accounts with the `OPERATIONS` role.
- Search orders by applicant ID or order ID.
- Status filtering across all lifecycle states.
- Detailed order inspection using the dedicated Operations API (`GET /api/v1/operations/orders/{order_id}`).
- Partner assignment and reassignment with recorded operational reasons.
- Lifecycle transition controls (Hold, Resume, Cancel, Simulated Activation).

### E. Partner Assignment & Fulfilment Workflow (`/partner`)
- Accessible only to accounts with the `PARTNER` role.
- Partner identity is derived exclusively from the verified signed session (`principal.username`).
- Partners see only orders currently assigned to them (`a.superseded_at IS NULL`).
- Partners cannot access unassigned orders or orders assigned to other partners (HTTP 403 Forbidden).
- Partners record progress notes and advance fulfilment (`FULFILMENT_IN_PROGRESS` → `FULFILMENT_COMPLETED` → `ACTIVATION_PENDING`).
- Partners cannot perform final activation (strictly reserved for Operations).

### F. Simulated Activation
- Triggered by Operations when an order reaches `ACTIVATION_PENDING`.
- Records operator identity, timestamp, and simulated activation metadata in the append-only event log.
- Strictly simulated for the competition prototype; explicitly communicates that no real telecom network provisioning or OSS/BSS integration has occurred.

### G. Customer Order Tracking (`/orders`)
- Customers view orders for their owned applicant profiles.
- Progress steps indicate current stage and next milestones.
- Displays the immutable pricing snapshot, line items, and estimated recurring totals.
- Displays a chronological event timeline recording each milestone, timestamp, and non-sensitive status explanations.
- Allows customer cancellation only while the order remains in `ORDER_PLACED`. Once assigned to a partner, customer self-cancellation is blocked (HTTP 409).

## 4. Database Schema & Migration Strategy

Persistence is implemented in the existing SQLite database (`backend/data/applicants.sqlite3`). Migration is handled automatically on startup through idempotent `CREATE TABLE IF NOT EXISTS` statements:

```sql
CREATE TABLE IF NOT EXISTS orders (
    order_id      TEXT PRIMARY KEY,
    applicant_id  TEXT NOT NULL,
    status        TEXT NOT NULL DEFAULT 'ORDER_PLACED',
    snapshot_json TEXT NOT NULL,
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL,
    FOREIGN KEY (applicant_id) REFERENCES applicants(applicant_id)
);

CREATE TABLE IF NOT EXISTS order_events (
    event_id        TEXT PRIMARY KEY,
    order_id        TEXT NOT NULL,
    event_type      TEXT NOT NULL,
    from_status     TEXT,
    to_status       TEXT NOT NULL,
    actor_username  TEXT NOT NULL,
    actor_role      TEXT NOT NULL,
    reason          TEXT,
    detail          TEXT,
    created_at      TEXT NOT NULL,
    FOREIGN KEY (order_id) REFERENCES orders(order_id)
);

CREATE TABLE IF NOT EXISTS order_assignments (
    assignment_id        TEXT PRIMARY KEY,
    order_id             TEXT NOT NULL,
    partner_username     TEXT NOT NULL,
    assigned_by_username TEXT NOT NULL,
    assigned_at          TEXT NOT NULL,
    reason               TEXT,
    superseded_at        TEXT,
    FOREIGN KEY (order_id) REFERENCES orders(order_id)
);

CREATE INDEX IF NOT EXISTS idx_orders_applicant ON orders(applicant_id);
CREATE INDEX IF NOT EXISTS idx_order_events_order ON order_events(order_id);
CREATE INDEX IF NOT EXISTS idx_assignments_order ON order_assignments(order_id);
CREATE INDEX IF NOT EXISTS idx_assignments_partner ON order_assignments(partner_username);
```

## 6. Known Prototype Limitations

1. **Commercial Terms**: Quotations and orders represent prototype order requests. Pricing is estimated and non-binding; no commercial contracts, payment processing, or payment gateways are integrated.
2. **Registry Integration**: GSTIN and Udyam registry validations run against supplied synthetic competition CSV datasets (`mock_gstin_registry.csv`, `mock_udyam_registry.csv`). No real government APIs are queried.
3. **Telecom Provisioning**: Activation is simulated within the application state machine; no network provisioning or telecom OSS/BSS workflows exist.
4. **Concurrency & Storage**: Concurrency control uses Python process-level re-entrant locks (`threading.RLock`) tailored for single-instance SQLite deployments. Multi-node production deployment requires PostgreSQL with row-level locking.
