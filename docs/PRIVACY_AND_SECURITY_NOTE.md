# Privacy & Security Note — UdyamOne (Airtel SYNC 2026 Prototype)

**Team**: PulseForge · **Document scope**: one-page competition privacy note, based strictly on the implemented prototype.

UdyamOne is a competition prototype demonstrating a connected digital-onboarding journey for MSMEs. It processes synthetic competition data and specimen documents only; no real customer data is collected or processed.

**Consent first.** Document upload, local OCR processing and registry comparison are blocked until the customer records an explicit, versioned consent decision (currently `kyc-consent-v2`), stored with its timestamp. Consent can be declined at any time; declining blocks the processing steps it covers.

**Data minimisation.** The prototype collects only what each step needs: a business profile (name, type, city, size, segment, requirement categories) for recommendations; KYC documents (GST certificate, Udyam certificate, signatory ID, address proof) only where the workflow requires them; and optional business name/address for mismatch warnings. We do not collect payment details, biometrics beyond what specimen images contain, or contact lists. Documents are stored under system-generated names — the client-supplied filename is not retained.

**Local OCR — documents stay on the application host.** Uploaded documents are processed on the backend host using Windows' built-in OCR engine, `pypdfium2` and Pillow. Document images and extracted text are **not** transmitted to Gemini, OpenAI or any other external AI service. The separate AI Business Advisor is a distinct, optional chat service: it sends only the business profile and chat messages the user types to the configured LLM provider, and never document contents or OCR output. If the advisor is not configured, it is disabled (HTTP 503).

**PII protection and human-in-the-loop corrections.** Original OCR extractions are preserved as evidence; customer corrections are stored separately and flagged (`correction_applied`), so manually corrected values are never presented as unmodified OCR output. Registry verification persists only the outcome (VERIFIED / MISMATCH / UNAVAILABLE / INCONCLUSIVE), the reason, compared/mismatched field names, a timestamp and a one-way input fingerprint — raw registry rows and submitted identifiers are not duplicated into applicant records. Document downloads are applicant-scoped, role-checked and served with `no-store`, `nosniff`, sandbox CSP and no-referrer headers.

**Synthetic registries — not government verification.** GSTIN and Udyam checks compare corrected fields against supplied synthetic competition datasets (`mock_gstin_registry.csv`, `mock_udyam_registry.csv`). No government GSTN or Udyam API is queried, and a match is not an official government verification.

**Access controls.** Four backend-configured roles (CUSTOMER, REVIEWER, OPERATIONS, PARTNER) use PBKDF2-SHA256 password hashes and short-lived (30-minute) HMAC-SHA256 signed sessions. For authenticated workflows, CUSTOMERS access their own configured KYC and order records; REVIEWERS access KYC through the review workflow; OPERATIONS manages orders and partner assignments; and PARTNERS access only orders currently assigned to them. KYC assessment and document-download endpoints permit CUSTOMER (own applicant) and REVIEWER access, rejecting OPERATIONS and PARTNER with HTTP 403. These protections are enforced server-side and covered by automated tests. Frontend navigation is convenience only and is never the security boundary.

**Known pre-KYC limitation.** The four applicant onboarding and quotation endpoints (`POST /api/v1/applicants`, `PUT /api/v1/applicants/{applicant_id}`, `GET /api/v1/applicants/{applicant_id}` and `POST /api/v1/applicants/{applicant_id}/quotes/preview`) currently have no session or role authorization. The three endpoints accepting an existing applicant ID do not enforce applicant ownership. A caller who knows an applicant ID may read or modify pre-KYC profile and recommendation data; the update operation also deletes existing quote previews. Opaque `APPL-` identifiers are not authorization. This is an accepted synthetic-data competition-prototype limitation and must be addressed before real customer data or production exposure.

**Document retention — current prototype behaviour.** There is **no automatic deletion or expiry** of uploaded documents or KYC records in this prototype: documents remain on the local application host (git-ignored `runtime_uploads/`) and manifests in the local SQLite database until manually removed by an operator. For production we propose — but have not implemented — a configurable retention period (approximately 90 days after a KYC decision, subject to the relevant telecom operator's approved records-retention policy), an approved deletion workflow with dual authorisation, and separate retention of minimal audit records (decisions, actors, timestamps) after document deletion.

**Prototype limitations.** HTTPS/encryption-at-rest, managed secrets, enterprise identity (MFA/SSO), malware scanning, rate limiting, server-side session revocation, centralised audit logging and automated retention are **not implemented** in this prototype and are documented as production requirements in `PRODUCTION_READINESS.md`. This note describes a competition prototype; it is not a compliance attestation (no DPDP Act / ISO 27001 / SOC 2 audit has been performed).
